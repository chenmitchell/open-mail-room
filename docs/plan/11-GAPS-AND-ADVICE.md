# 11 你原本思慮不周之處與改善建議

(依影響排序;全部已回填進 01~08 規格)

## 高影響

1. **LINE Notify 已死**:2025/3/31 停用。若照原構想做會直接做不出來。改用 LINE OA + Messaging API,但免費只有 200 則推播/月——中型公司一天就能用完。因此通知必須是多 adapter,並把「通用 webhook」做成一等公民,讓公司串自己的免費管道(Telegram、內部 IM)。
2. **條碼優先,AI 其次**:託運單號用 AI OCR 是浪費——標籤上本來就有條碼,前端 ZXing 掃碼免費、即時、近乎 100% 準。AI 只該處理條碼給不了的:寄件人、收件人、手寫。這一項能把 AI 成本砍掉大半,也是你原案最大的優化空間。
3. **API Key 放哪**:「讓人填 API key」若做在前端會被瀏覽器 devtools 直接偷走。Key 必須只存後端(加密),前端永遠只看到遮罩。開源套版者會犯這錯,文件要用粗體警告。
4. **個資法**:姓名+照片+電話是個人資料。需要:蒐集告知文案、保存期限自動刪除/匿名化(預設 5 年)、稽核紀錄、照片去 EXIF(內含 GPS)。開源發布時這是台灣使用者的合規賣點,別人都沒做。
5. **AI 掛掉系統不能跟著掛**:OCR 必須是「增強」不是「依賴」——沒 key、沒網路、額度爆掉時,純手動+掃碼流程要完整可用。同時要有月預算上限,防止被灌爆帳單。

## 中影響

6. **離線場景**:收發室常在地下室/電梯間,收訊差。PWA 要做離線佇列(IndexedDB 暫存,回線補送),否則第一線會棄用。
7. **簽收存證**:糾紛(「我沒收到」)是收發室最常見的痛。領取需要簽名圖檔或取件碼核銷+時間戳,機密件加查看稽核。你原案只提到「人工確認儲存」,沒提領取核銷閉環。
8. **名錄維運**:OCR 對應部門的前提是員工名錄是活的——同名同姓、英文名/暱稱、離職、部門改組都要處理(aliases 欄位、離職警示、部門冗餘欄位)。名錄 CSV 匯入是 v1 必備,不是 nice-to-have。
9. **機密件**:法務文件、薪資單、雙掛號存證信函不能拍內容、通知不能顯示寄件人。需要 confidential 旗標與專屬處理流程。
10. **實務欄位**:貨到付款(櫃台代墊糾紛)、冷藏冷凍(放到臭掉誰負責)、代領、退回、轉寄、逾期招領/銷毀——傳統簽收簿都有這些,數位化不能少。

## 較低影響但建議想清楚

11. **授權選擇**:建議 AGPL-3.0——防止雲端商閉源轉賣;若你更在乎採用率(企業法務怕 AGPL)則選 MIT。這是社群策略選擇,寫進 DECISIONS 即可,我在規劃中預設 AGPL。
12. **手寫中文是 OCR 天花板**:LLM Vision 對手寫繁中收件人準確率明顯低於印刷體;規格已用「信心分數+候選清單+人工確認」兜底,預期不要設在「全自動」。
13. **iOS PWA 限制**:推播需 16.4+ 且加入主畫面;相機用 input capture 最穩。已在 06 設計降級路徑,但「iPhone 上不如原生 App 順」要在 README 誠實寫明。
14. **貨態自動追蹤別碰(v1)**:台灣各物流商 API 都要契約申請,開源專案拿不到通用授權;用爬蟲則脆弱且有法律風險。留 plugin 介面讓有契約的公司自己接。
15. **備份與金鑰**:加密做得越好,金鑰遺失越致命。安裝腳本要強制引導備份 `OPENMAILROOM_ENCRYPTION_KEY`,文件要有還原演練章節。
16. **多租戶**:有人會想拿去做 SaaS 服務多家公司。v1 明確不做(複雜度倍增),但資料模型避免寫死單租戶假設(檢查點寫進 M0 review)。
17. **可考慮的差異化加分項(v2+)**:員工出示 QR 快速核銷看板、櫃台大屏待領清單、Ollama 本地模型完全離線 OCR(機密環境賣點)、SCIM/AD 名錄同步。

## 對「無人值守開發」的提醒

18. 無人值守最大的風險不是寫不出來,是**燒 token 在死循環**(同一個錯修 10 次)與**靜默偏離規格**。已設計:3 輪修不過就 blocked 跳下一個、審查代理獨立 context、blocked ≥3 停機等人。請保留這些保險絲,不要為了「一直開發下去」拿掉。
19. Code Review 代理與實作代理**必須是不同 context**,否則審查者會繼承實作者的盲點,review 形同虛設。
